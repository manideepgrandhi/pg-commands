    security
    

    Roles, audits, SSL, row-level security and logging for PostgreSQL 13–17. RDS/Aurora marks items that only apply there. On RDS the master user is a member of rds_superuser, not a real superuser, and server settings go in the parameter group.

    role.sql
    
  
    

    

    
  
    Database role model (reader / writer / app_user)
    
  
    Generates a re-runnable psql script that creates a NOLOGIN owner and three access roles chained by membership. It validates its inputs and stops on the first error, then prints a verification report.
    
  
    
    Privilege model
    
    RoleGetsHow
    
    
      
    owner {db}_ownerOwns the database, schemas and all objects. Runs DDL and migrations via SET ROLE.NOLOGIN. The admin running the script is granted it (required on RDS: master user → owner).
    
      
    reader {db}_readerCONNECT; USAGE on the schemas; SELECT on tables, views and sequencesDirect grants plus ALTER DEFAULT PRIVILEGES FOR ROLE owner for future objects
    
      
    writer {db}_writerreader + INSERT/UPDATE/DELETE (TRUNCATE optional); USAGE/SELECT/UPDATE on sequences; EXECUTE on functionsGRANT reader TO writer (inherits), plus its own grants and default privileges
    
      
    app_user {db}_app_userwriter + TEMP tables. The role the application connects with; no CREATE anywhere, so no DDL.GRANT writer TO app_user; search_path set to the managed schemas
    
      
    PUBLICNothing (with the revoke option): no CONNECT/TEMP on the database, no CREATE in schema public, no EXECUTE on new functionsREVOKE … FROM PUBLIC
    
    
    
  
    Keep current owners (existing databases, e.g. Aurora): the owner row above doesn't apply. Objects keep their owners, and each one is granted to reader/writer individually. Default privileges are added FOR ROLE each role that owns objects in the managed schemas (auto-detected or listed), so future objects from any of them are covered. Foreign tables get the same table grants. Querying them also needs a user mapping for the role (or PUBLIC). USAGE on the foreign server is optional; it only lets reader create its own user mappings or foreign tables.
    
  
    Why membership: each privilege is granted once, so writer can never fall behind reader. The roles must be INHERIT, which the script enforces. A NOINHERIT role would only get the privileges after SET ROLE, which apps don't do. People get access by being granted one of the three roles (GRANT {db}_reader TO alice). RDS/Aurora: there's no superuser, so run it as the master user (rds_superuser, CREATEROLE, CREATEDB). The script grants the owner role to that user, because CREATE DATABASE … OWNER, SET ROLE and ALTER DEFAULT PRIVILEGES FOR ROLE all require it.
    
  
    
    
    Default for -v database_name.
    
    
    Comma-separated managed schemas, e.g. public, app. The first one hosts the verification test.
    
    
    Create stops if the DB exists; extend stops if it doesn't.
    
    
    {db} is replaced with the database name.
    
    
    Read-only.
    
    
    Read + DML.
    
    
    What the application logs in as.
    
    
    Creates them with LOGIN and no password; set one with \password. The owner never logs in.
    
    
    REVOKE ALL ON DATABASE, CREATE ON SCHEMA public and EXECUTE on new functions FROM PUBLIC.
    
    
    No owner role, no ALTER … OWNER, no CREATE DATABASE. Grants each object as it is; default privileges FOR ROLE each object creator.
    
    
    Comma-separated. Empty: every role that owns objects in the managed schemas.
    
    
    Querying a foreign table needs SELECT on it plus a user mapping for the querying role (or PUBLIC). Server USAGE is only needed to create foreign tables or your own user mappings.
    
    
    Off by default: TRUNCATE skips DELETE triggers and RLS.
