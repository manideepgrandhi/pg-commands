Database role model (reader / writer / app_user)

  
Generates a re-runnable psql script that creates a NOLOGIN owner and three access roles chained by membership. It validates its inputs and stops on the first error, then prints a verification report.

  

    Privilege model
    
RoleGetsHow

    
      
owner {db}_ownerOwns the database, schemas and all objects. Runs DDL and migrations via SET ROLE.NOLOGIN. The admin running the script is granted it (required on RDS: master user → owner).

      
reader {db}_readerCONNECT; USAGE on the schemas; SELECT on tables, views and sequencesDirect grants plus ALTER DEFAULT PRIVILEGES FOR ROLE owner for future objects

      
writer {db}_writerreader + INSERT/UPDATE/DELETE (TRUNCATE optional); USAGE/SELECT/UPDATE on sequences; EXECUTE on functionsGRANT reader TO writer (inherits), plus its own grants and default privileges

      
app_user {db}_app_userwriter + TEMP tables. The role the application connects with; no CREATE anywhere, so no DDL.GRANT writer TO app_user; search_path set to the managed schemas

      
PUBLICNothing (with the revoke option): no CONNECT/TEMP on the database, no CREATE in schema public, no EXECUTE on new functionsREVOKE … FROM PUBLIC

    

  
Why membership: each privilege is granted once, so writer can never fall behind reader. The roles must be INHERIT, which the script enforces. A NOINHERIT role would only get the privileges after SET ROLE, which apps don't do. People get access by being granted one of the three roles (GRANT {db}_reader TO alice). RDS/Aurora: there's no superuser, so run it as the master user (rds_superuser, CREATEROLE, CREATEDB). The script grants the owner role to that user, because CREATE DATABASE … OWNER, SET ROLE and ALTER DEFAULT PRIVILEGES FOR ROLE all require it.
